Git sin miedo: el flujo de ramas que usamos en equipo

6 nov 2026 · 3 min · #git#equipo

La primera vez que trabajé en equipo con Git, el miedo era siempre el mismo: "¿y si borro el trabajo de alguien?". Con un flujo simple ese miedo desaparece. Este es el que usamos en el bootcamp.

Las ramas

  • main: solo código estable, lo que se puede mostrar.
  • develop: donde se integra el trabajo del sprint.
  • feature/nombre-tarea: una rama por cada tarea.

El ciclo de cada tarea

git checkout develop
git pull origin develop
git checkout -b feature/consulta-disponibilidad
# ...programo y hago commits pequeños...
git add .
git commit -m "feat: consulta de disponibilidad por fecha"
git push origin feature/consulta-disponibilidad
# luego abro un Pull Request hacia develop

Tres reglas que nos salvaron

  1. Commits pequeños con mensajes claros (feat:, fix:, docs:).
  2. Hacer pull antes de empezar, todos los días.
  3. Nadie hace merge de su propio PR: alguien más lo revisa.

¿Y los conflictos?

No son un error, son una conversación. Git te muestra las dos versiones, decides con tu compañero cuál queda (o combinas ambas), haces commit y listo.

Un buen equipo no es el que no tiene conflictos, sino el que sabe resolverlos.
